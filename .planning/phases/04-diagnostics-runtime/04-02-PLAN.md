<objective>
Implement the capture_screenshot MCP tool that captures a screenshot of the running Godot game and returns it as a base64-encoded PNG for AI visual inspection.

Purpose: This enables an AI to visually inspect a running Godot game, closing the feedback loop between code changes and visual results. The tool uses a GDScript autoload injected into the game process that monitors a trigger file to capture the viewport on demand.

Output: `src/scripts/screenshot_helper.gd` (autoload script), updated `src/tools/editor.ts` (new capture_screenshot tool), and `tests/screenshot-tools.test.ts`.
</objective>

  <behavior>
    - capture_screenshot returns toolError when ctx.activeProcess is null (no game running)
    - capture_screenshot returns toolError when screenshot file is not produced within timeout
    - capture_screenshot returns MCP image content with type: 'image', mimeType: 'image/png', and base64 data when screenshot succeeds
    - capture_screenshot writes a trigger file that the GDScript autoload detects
    - capture_screenshot reads the resulting PNG file and returns it as base64
  </behavior>
  <action>
    1. Create `src/scripts/screenshot_helper.gd`:
       - Extends Node, designed as an autoload
       - In `_ready()`: parse command-line args for `--screenshot-trigger` and `--screenshot-output` paths
       - In `_process(delta)`: poll trigger_path every 0.5s using FileAccess.file_exists()
       - When trigger file detected: delete it, await RenderingServer.frame_post_draw, capture viewport via `get_viewport().get_texture().get_image()`, save PNG to output_path
       - Do NOT call `flip_y()` (not needed in Godot 4.x per research)

    2. Modify `src/tools/editor.ts` to add `capture_screenshot` tool:
       - Input schema: `project_path` (string, required) — the project directory
       - Implementation:
         a. Check `ctx.activeProcess` is not null, return toolError if no game running
         b. Create temp paths for trigger and output files using `os.tmpdir()` and a unique suffix
         c. Write the trigger file (empty file, `fs.writeFileSync(triggerPath, '')`)
         d. Poll for the output PNG file with 100ms intervals, timeout after 5 seconds
         e. Read the PNG file, convert to base64 via `Buffer.from(readFileSync(outputPath)).toString('base64')`
         f. Clean up temp files (trigger and output)
         g. Return MCP image content: `{ content: [{ type: 'image', data: base64, mimeType: 'image/png' }] }`
       - NOTE: The screenshot_helper.gd autoload must be loaded by the game. The user must configure it as an autoload in their project.godot, OR the tool documentation should instruct to use `run_project` with the autoload flag. For this plan, add a note in the tool description that the game must be started with the screenshot helper autoload. A future enhancement could auto-inject it.

    3. IMPORTANT DESIGN DECISION: Rather than requiring users to configure autoloads manually, modify `run_project` to accept an optional `enable_screenshot` boolean parameter. When true, run_project adds `--` followed by `--screenshot-trigger <triggerPath> --screenshot-output <outputPath>` as user arguments that the screenshot_helper.gd autoload reads. Store these paths on the ServerContext (add `screenshotTriggerPath` and `screenshotOutputPath` optional fields to ServerContext in types.ts if needed, or store them alongside activeProcess). The capture_screenshot tool then uses these stored paths.

       Actually, simplest approach per research: pass the trigger/output paths as custom command-line args when spawning the game. The screenshot_helper.gd reads them from `OS.get_cmdline_user_args()`. This means run_project needs to be updated to always pass these args (the helper script is a no-op if the trigger file is never created). BUT this requires the user to have screenshot_helper.gd registered as an autoload in their project.

       SIMPLEST VIABLE APPROACH: The capture_screenshot tool itself handles the coordination:
       - It checks ctx.activeProcess exists
       - It writes a trigger file at a known path (e.g., `{project_path}/.godot/screenshot_trigger`)
       - The GDScript helper polls for this file at the known project-relative path
       - The output goes to `{project_path}/.godot/screenshot.png`
       - This avoids needing to pass CLI args and works with any running game that has the autoload

       Use this approach. The tool description should note that `ScreenshotHelper` must be added as an autoload to the Godot project for capture_screenshot to work.

    4. Write `tests/screenshot-tools.test.ts`:
       - Mock fs.writeFileSync, fs.readFileSync, fs.existsSync, fs.unlinkSync
       - Test: no active process returns error
       - Test: screenshot file not produced within timeout returns error
       - Test: successful capture returns image content with correct structure
       - Follow existing test patterns from tests/scene-tools.test.ts
